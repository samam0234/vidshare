개요

기동 구조

Express 4 + TypeScript 기반 REST API 서버입니다. 데이터는 PostgreSQL 16 에 저장되고, 업로드 파일은 디스크(UPLOADS_PATH)에 UUID 이름으로 떨어집니다. DB에는 /uploads/<uuid>.ext 경로 문자열만 들어가서, 파일 위치를 바꿔도 스키마를 건드릴 필요가 없습니다.

부팅은 index.ts → http.createServer(app) → attachChatSocket(server) 순서입니다. WebSocket이 같은 HTTP 서버에 업그레이드로 붙기 때문에 포트를 하나만 씁니다.

서버가 자기 API 목록을 스스로 말합니다. GET / 로 요청하면 등록된 82개 엔드포인트가 JSON으로 돌아옵니다. 별도 API 문서를 손으로 유지하는 대신 app.ts 의 라우트 등록에서 목록을 만들어, 라우트를 추가하고 문서 갱신을 잊는 상황을 없앴습니다.

기술역할선택 이유
Express 4HTTP 서버라우트 파일이 곧 API 목록이 됩니다. NestJS의 모듈·DI는 이 규모에 설정 비용이 더 컸습니다.
TypeScript (tsx)언어 · 개발 실행응답 타입을 프론트와 공유합니다. 개발은 tsx watch, 배포는 tsc 빌드.
PostgreSQL 16 (pg)데이터베이스버전 관리 마이그레이션(schema_migrations)과 pg_dump 백업. 로컬은 내 PC 의 D 드라이브, 운영은 VM 블록 볼륨.
bcrypt비밀번호 해시평문을 어디에도 남기지 않습니다.
wsWebSocket같은 HTTP 서버에 업그레이드로 붙어 포트를 하나만 씁니다.
multer파일 업로드multipart 파싱. MIME 화이트리스트와 용량 제한을 여기서 겁니다.
LangChain · LangGraphAI 파이프라인모델 티어마다 구조 자체를 다르게 만들 수 있습니다 (단순 체인 / 상태 그래프).
node --test + supertest테스트런타임 내장 러너. Jest/Vitest 설정 없이 148건이 돕니다. 테스트 파일마다 고유 스키마로 격리.
Caddy · systemd운영 (Oracle VM)Caddy 가 HTTPS 인증서를 자동으로 받고 /uploads 를 디스크에서 직접 줍니다. Node 는 systemd 가 관리합니다.
SQLite 로 시작해서 배포 전에 PostgreSQL 로 옮겼습니다. 처음 배워야 할 것은 스키마 설계와 쿼리 격리였고, 그건 설치 없는 SQLite 로 충분했습니다. 상시 서버에 올리기로 하면서 마이그레이션 이력과 백업 도구가 필요해져 전환했습니다. 동기 API 를 비동기로 바꾸는 일이라 store.ts 와 라우트 25개가 전부 await 를 새로 배웠지만, SQL 문장과 컬럼 타입은 그대로 두어 기존 테스트 137건이 수정 없이 통과하는 것을 합격 기준으로 삼았습니다.

인증 · 세션

  • 비밀번호는 bcrypt 해시. 평문은 어디에도 남기지 않습니다.
  • 세션은 DB sessions 테이블에 저장하고 쿠키는 HttpOnly.
  • 사용자/관리자 세션은 쿠키 이름과 검증 함수 모두 분리 (requireRequestUser / requireAdmin).
  • 계정 정지 시 그 유저의 세션 행을 즉시 삭제 → 이미 열린 창도 다음 요청에서 끊깁니다.

1. LangChain · LangGraph 기반 챗봇 3티어

모델을 세 등급으로 나누되, 티어마다 파이프라인 구조 자체를 다르게 만들었습니다. 같은 체인에 모델 이름만 바꿔 끼우는 방식이었다면 티어를 나눌 이유가 없었습니다.

Shape의 RAG — 서비스 문맥을 아는 챗봇

전송 전에 프론트에서 collectChatCorpus()(과거 대화)와 collectPlatformCorpus()(플랫폼 데이터 스냅샷)로 컨텍스트를 모읍니다. 덕분에 "내가 올린 영상이 몇 개냐" 같은 서비스 문맥 질문에 답할 수 있습니다. 일반적인 문서 임베딩 RAG가 아니라, 플랫폼 자신의 상태를 코퍼스로 쓰는 형태입니다.

멀티모달 첨부 — 모델별 입력 능력 차이를 흡수

// 이미지 / PDF / DOCX 첨부 Locals · Vide → Gemini 비전에 직접 전달 Shape → Gemini 로 먼저 설명 텍스트를 만든 뒤 Groq 모델에 넘김 (Groq 쪽 모델은 이미지를 직접 받지 못하므로)
해결한 문제 — 라이브러리가 타임아웃을 무시했습니다.
증상: 챗봇이 응답 없이 몇 분을 매달린 뒤 ETIMEDOUT 이 사용자 화면에 그대로 노출됐습니다.
원인: @langchain/google-genai 는 timeout 옵션도 AbortSignal 도 실제 HTTP 요청에 전달하지 않습니다. 우리 쪽에서 끊을 수단이 없어 OS TCP 타임아웃까지 기다린 것입니다.
해결: llm.ts 에 withTimeout() 을 만들어 Promise.race 로 한 겹 더 감쌌습니다. CHAT_TIMEOUT_MS(기본 45초) 상한에서 잘라 내고, 내부 오류 문자열 대신 504 + 안내 문구로 바꿉니다.
남긴 것: 새 모델 호출을 추가할 때 반드시 withTimeout(llm.invoke(…)) 로 감싸라는 규칙을 README에 명시했습니다. 라이브러리가 고쳐질 때까지 유효한 제약이라, 코드가 아니라 문서에 남겨야 다음 사람이 압니다.

해결한 문제 — 비회원이 임의의 이름으로 댓글을 달 수 있었다

증상 — 댓글 작성 API가 author 를 요청 본문에서 그대로 받고 있었습니다. 로그인하지 않아도 아무 이름으로 댓글을 쓸 수 있었습니다.

해결 — 댓글 작성에 requireRequestUser() 를 강제하고, 작성자를 세션에서만 가져오도록 바꿨습니다. 클라이언트가 보낸 author 는 무시합니다.

배운 것 — "클라이언트 상태는 신뢰할 수 없다"는 원칙을 알고 있었는데도, UI에 로그인 버튼이 있다는 이유로 서버 검사를 빠뜨렸습니다. UI의 존재는 보안 경계가 아닙니다. 이 일 이후 쓰기 API를 전부 훑어 requireRequestUser() 누락을 점검했습니다.
