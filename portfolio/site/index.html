01 · 프로젝트 소개

운영까지 넣으니 설계할 것이 달라졌다

영상 플레이어 하나를 만드는 과제로는 배울 것이 금방 끝납니다. 그래서 콘텐츠 소비 → 창작 → 소통 → 운영까지 서비스가 실제로 도는 한 사이클을 전부 통과해 보기로 했습니다.

운영을 범위에 넣은 것이 이 프로젝트의 성격을 결정했습니다. 신고가 들어오면 누가 보고 무엇을 근거로 지우는지, 정지된 계정의 세션은 언제 끊기는지 — 이런 질문은 사용자 화면만 만들어서는 마주칠 일이 없습니다. 관리자 콘솔을 별도 앱으로 분리하면서 비로소 권한 경계를 설계해야 했습니다.

시스템 구성

[Browser — 사용자] [Browser — 운영자] │ │ ▼ ▼ [FrontServer :3000] [console :3200] Next.js · lib/api.ts Next.js · lib/adminApi.ts 쿠키 vidshare_sid 쿠키 vidshare_admin_sid │ │ └────── fetch(credentials: "include") ┘ │ ▼ [BackendServer :4000] Express REST API routes/ → data/store.ts → db/client.ts /api/* ← requireRequestUser /api/admin/* ← requireAdmin /ws/conversations (WebSocket) /api/notifications/stream (SSE) │ ▼ [PostgreSQL 16] 22 tables + schema_migrations [Files] UPLOADS_PATH (DB엔 경로 문자열만)

끝까지 지킨 설계 원칙 4가지

1. 응답은 한 가지 형태만

모든 API가 { success, data?, error? } 를 돌려줍니다. 프론트가 응답마다 다른 분기를 만들 필요가 없습니다.

2. 인증은 라우트 첫 줄에서

인증이 필요한 라우트는 requireRequestUser(req) 로 시작해 세션이 없으면 그 자리에서 401을 던집니다. 본문에 인증 분기가 섞이지 않습니다.

3. 소유자 스코프는 쿼리에서 격리

알림·대화·재생목록은 전부 WHERE owner_id = ? 로 거릅니다. 남의 데이터가 섞일 수 있는 경로를 아예 만들지 않습니다.

4. 프론트의 통신 창구는 하나

lib/api.ts 를 거치지 않는 fetch 를 금지했습니다. 쿠키·베이스 URL·에러 규약이 한 파일에만 있습니다.

백엔드를 Workers에 올리지 않은 이유. DB 와 업로드 파일은 영구 디스크가, SSE·WebSocket 은 상시 프로세스가 필요합니다. Workers 런타임에는 둘 다 없습니다. 처음엔 내 PC 를 Cloudflare Tunnel 로 노출하려 했지만 PC 가 꺼지면 서비스도 멈춰서, 블록 볼륨이 붙은 VM 1대로 정했습니다. 최초 설정·반복 배포·백업 스크립트까지 준비했고 VM 구축과 도메인 연결이 남았습니다. 그 전까지 배포된 프론트는 UI 확인용입니다.

SQLite → PostgreSQL 전환

바꾸지 않을 것부터 정했다

동기 API(better-sqlite3)를 비동기(pg)로 바꾸며 store.ts 1,600줄과 라우트 25개가 전부 await 를 새로 배웠습니다. SQL 문장과 컬럼 타입은 그대로 두었기에 "기존 테스트 137건이 한 줄도 안 바뀌고 통과"가 곧 합격 기준이 됐습니다. 실데이터 151행은 이관 스크립트로 옮기고 행 수를 대조했습니다.

타입체크가 못 잡는 것

Express 4 는 async 핸들러의 실패를 놓쳐 401 이 응답 없이 매달립니다 — 라우터를 감싸 해결했습니다. { ...getPlaylistById(id) } 처럼 Promise 를 spread 하면 TypeScript 가 경고 없이 {} 를 만듭니다. await 없는 async 호출을 스크립트로 전수 검사했고, 뒤늦게 E2E 가 개발 DB 로 조용히 성공하던 것도 찾아 고쳤습니다.

회고

잘한 결정

  1. 관리자 콘솔을 별도 앱으로 분리한 것. 쿠키 이름을 나눈 사소한 결정 하나가 "두 세션이 공존해야 한다"는 요구를 드러냈습니다.
  2. lib/api.ts 단일 창구 규약. localStorage → SQLite 이관도, 크로스 도메인 쿠키 대응도 고칠 지점이 한 곳이었습니다. DB 를 Postgres 로 바꿀 때 프론트는 한 줄도 바뀌지 않았습니다.
  3. 한계를 문서에 적어 둔 것. 모르는 것과 알고 미룬 것은 다릅니다.

아쉬운 점

  1. CI를 늦게 깐 것. 테스트를 170건 넘게 만들고도 한동안 수동으로 돌렸습니다. 지금은 GitHub Actions 가 돌리지만 처음부터 깔았어야 했습니다.
  2. data/store.ts 가 1,500줄이 되도록 방치한 것. 초반에 도메인별로 나눴다면 지금 분할 비용이 없었습니다.
  3. 성능·접근성을 측정한 적이 없는 것. 기능이 안정된 지금이 기준선을 잡을 시점입니다.
