## 2. 개요

### 배경

093에서 포트폴리오 문서(md·docx)와 소개 사이트를 만들었지만, 둘 다 "읽는" 자료다.
발표·면접 자리에서 화면을 넘기며 설명할 자료가 없었다. 사용자가 요청한 형태는
**"코드 리뷰보단 그냥 사이트 소개 식으로"** — 즉 구현을 설명하는 덱이 아니라
서비스가 무엇을 하는지 보여주는 덱이다.

### 목표

- API 엔드포인트·파일 구조·트레이드오프 같은 구현 디테일 없이
- 화면 스크린샷이 각 슬라이드의 주인공인 23장짜리 덱
- 실제로 PowerPoint에서 열리고 편집 가능한 `.pptx` 파일

### 범위 (In Scope)

- `portfolio/build_pptx.py` — python-pptx 기반 슬라이드 생성기

- 커버 → 목차 → 프로젝트 소개 → 핵심 기능 → 사용자 화면 4장 → AI 챗봇 →
  관리자 콘솔 2장 → 기술 스택 → 규모 → 회고 → 다음 계획 → 클로징

## 4. 결정과 트레이드오프

### 왜 python-pptx로 프로그램 생성했나

손으로 PowerPoint를 만들면 이 대화 세션 안에서 검증할 수 없다. `python-pptx` 로
슬라이드를 코드로 생성하면 문구를 고칠 때마다 스크립트를 다시 돌리기만 하면 되고,
**PowerPoint COM 자동화로 실제로 열리는지, 렌더링이 깨지지 않는지 이 자리에서
검증**할 수 있었다. 실제로 이 방식 덕분에 아래 4장에 적은 버그 세 건을 전부
"에이전트가 만들어 놓고 확인 안 한 산출물"이 아니라 눈으로 보고 고친 결과로
남길 수 있었다.

### 데이터와 레이아웃을 분리

`text()`, `rect()`, `browser_frame()`, `phone_frame()` 같은 저수준 헬퍼와
`build()` 안의 슬라이드별 문구·화면 목록을 나눴다. 문구를 고치는 사람이
좌표 계산까지 이해할 필요가 없게 하려는 목적이다.

### 스크린샷 프레이밍 — 브라우저 vs 폰

쇼츠 피드는 세로 영상 앱이라 **폰 목업**(`phone_frame`)을 새로 만들어 썼다.
초안은 데스크톱 스크린샷을 브라우저 프레임에 넣고 옆에 모바일 스크린샷을
작게 곁들이는 구성이었는데, 좁은 상자에 넓은 화면(1440×900)을 욱여넣어
결과물이 작고 어색했다(4장 참고). 세로 영상은 세로 프레임에 담는 것이
화면 성격에 맞다고 판단해 통째로 바꿨다.

## 5. 작업 중 잡은 버그

프로그램으로 생성한 뒤 **PowerPoint COM 자동화로 실제 열어서 PNG로 내보내
눈으로 검증**하는 과정에서 세 가지를 발견했다. python-pptx나 다른 파서로
다시 읽는 것만으로는 드러나지 않는 종류였다.

| # | 증상 | 원인 | 조치 |
|---|------|------|------|
| 1 | **PowerPoint가 파일을 열지 못함** ("PowerPoint could not open the file") | `shape.shadow.inherit = False` 가 빈 `<a:effectLst/>` 를 이미 심어 두는데, 그림자 효과를 위해 새 `<a:effectLst>` 를 또 append해 같은 부모 아래 요소가 두 번 생김 — OOXML 스키마 위반. python-pptx로 다시 읽으면 문제없이 파싱되지만(관대한 파서) 실제 PowerPoint는 엄격하게 거부한다 | `rect()` 헬퍼에서 기존 빈 `effectLst` 를 찾아 **그 안을 채우는** 방식으로 변경 |
| 2 | 쇼츠 화면 슬라이드에서 스크린샷이 작고 어색함 | 넓은 데스크톱 스크린샷(1440×900)을 좁은 상자(3.1in)에 강제로 맞추면서 종횡비 때문에 실제 크기가 크게 줄어듦 | 세로 영상에 맞는 `phone_frame()` 헬퍼를 새로 만들어 폰 목업 하나로 크게 표시 |
| 3 | 섹션 구분 슬라이드에서 부제목이 2줄 제목과 겹침 | 부제목 y좌표를 "제목이 1줄"이라고 가정하고 고정했는데, 이 덱의 모든 섹션 제목이 실제로는 2줄이었음 | 제목 상자 높이·부제목 y좌표를 2줄 제목 기준으로 재계산 |
| 4 | 본문 문단에서 단어가 어색하게 잘림(`애플리케이션` 이 혼자 한 줄을 차지하는 등) | `word_wrap=True` 로 자동 줄바꿈되는 상자에 **수동으로 `\n` 을 더 넣어** 두 종류의 줄바꿈이 충돌 | 문단 중간의 수동 개행을 제거하고 진짜 문단 구분(`\n\n`)만 남김 |
| 5 | 목차 슬라이드 마지막 행이 하단 푸터와 겹침(레이아웃상 0.27in 침범) | 7개 행의 누적 높이를 계산할 때 슬라이드 하단 푸터 위치를 고려하지 않음 | 행 높이·간격을 줄여 7행 전체가 푸터 위에서 끝나도록 재계산 |

1번이 가장 중요하다 — **파일이 통째로 안 열리는 문제**였고, python-pptx로
재확인하는 정도로는 절대 잡히지 않았다. PowerPoint COM으로 직접 열어
PNG로 내보내 눈으로 훑는 검증 단계가 없었다면 그대로 커밋됐을 것이다.

## 6. 검증

```bash
pip install python-pptx
python portfolio/build_pptx.py    # 생성: 23장
```

**PowerPoint COM 자동화로 실측**(PowerShell):

```powershell
$ppt = New-Object -ComObject PowerPoint.Application
$pres = $ppt.Presentations.Open($pptPath)   # 정상적으로 열림, 23장 확인
$pres.SaveAs($outDir, 18)                   # 슬라이드마다 PNG로 내보내기
```

내보낸 PNG 23장을 전부 육안으로 확인했고, 의심스러운 지점(포인트 텍스트 아래
줄 같은 것)은 픽셀 단위로 분석해 실제 결함인지 렌더링 착시인지 구분했다
(해당 건은 한글 받침 획이 겹쳐 보이는 착시로 판명, 버그 아님).

## 7. 리스크 · 알려진 이슈

- 이 스크립트가 만든 `<a:effectLst>` 재사용 패턴은 python-pptx가 내부적으로
  `shadow.inherit` 를 구현하는 방식에 의존한다. 라이브러리 버전이 바뀌면
  다시 깨질 수 있다 — 새 그림자 효과를 추가할 때는 반드시 PowerPoint COM으로
  열리는지 검증할 것.
- 슬라이드 안 수치(15,700줄, 82 API, 22 테이블 등)는 093과 마찬가지로 수동 갱신이다.
- 이모지 아이콘(▶💬⚡🤖 등)은 PowerPoint의 기본 이모지 폰트로 렌더링된다.
  다른 OS/폰트 환경에서 열면 모양이 달라질 수 있다.
